# 訂錯貨退貨與重新下單（2026-10-17）

## 業務決策

公司較常遇到訂錯商品，而非瑕疵換貨。主要流程改為：原訂單申請退貨→實收並依品質處置→退回數量結案、不補送→需要其他商品時重新建立一般訂單。部分退貨不取消其他品項或原單未退數量。退款、折讓或抵用仍是獨立事項，本批不自動變更款項。

現行前端 customer-cancellations 的申請／實收已使用 CLOSE，不重做這條流程。demo-yushin 的 commitLocationReturn 在新請求未指定 settlement 時改用 CLOSE；明確指定的歷史 REPLACE 契約保留，已提交 hash／重試不變。不會把已存在的 REPLACE 預留自動釋放或改寫，也不更改舊資料的缺欄解讀／共用核心預設值。後續同單免費補送開發暫緩。

## 新增操作

訂單進度的退貨／取消頁籤，在可管理該訂單且已有 qty>0 的 CLOSE 實收紀錄時，顯示「退貨後重新下單」。未實收的申請與 REPLACE 紀錄不顯示入口。

操作會關閉原進度視窗，呼叫既有 openOrderModal() 開啟乾淨新單：只填客戶、交易類型／發票抬頭及原單參考備註。商品、數量、價格、採購／庫存進度及收款狀態不複製；使用者必須重新選商品並確認數量／價格，再按一般建單的儲存。新單可以購買不同商品及數量，不被原退貨額度限制；這不是免費補送。

新單以 returnReorderSource={orderId} 保存單向來源關聯，原單不加 backlink、不自動建第二份訂單，也不轉移預留。該關聯隨既有草稿保存／恢復，開啟其他新單或關閉清除時重設，不與 quote／forecast 來源同步混用。備註含原單號，結構化來源關聯不依賴使用者是否修改備註。

## 提交、權限與效能

真正提交仍只有 commitOrderCreation。新增來源關聯時同交易讀原 orders，核對來源存在、客戶一致、具有實收 CLOSE 退貨；sales／engineer 限本人原單，admin／purchaser 沿既有讀取範圍。入口不擴大角色權限；purchaser 並未因本批取得訂單生命週期按鈕。

首次建單增加一次原訂單文件讀取，只寫新 orders；不讀寫原單庫存、預留、批次、退貨、款項或成本。新單沿既有庫存初始化及來源同步 checkpoint，不宣稱完整建單＋預留原子化。這是一般有價新單，價格由使用者重新確認，不以零價代表補送。

沿用固定 pendingOrderCreateKey 防止回覆不明時另開新單。已提交重送只讀取既有新單，不覆蓋新進度；若 pending ID 已關聯不同退貨來源（含一般單與來源單互換）則拒絕。已成功後的來源刪改不會把重送變成重建。來源關聯只供查核，不授予讀取、扣帳或款項權限；底層正式存取仍由現有 Rules 控制，本批不改 Rules／索引。

## 驗證與尚未完成

測試涵蓋乾淨新單入口、來源／客戶／身分驗證、未實收／REPLACE 拒絕、來源單不變、正常商品價格保留、重送與 pending ID 來源衝突；Emulator 驗證未指定 settlement 真正增加自由實貨而不恢復原單預留，並驗證原 REPLACE 回覆重送相容。完整 CI 另驗證全部 Node、Rules、Emulator／Callable 與六組桌機／手機 Chrome。

GitHub 合併不代表 Firebase 部署。新單入口尚未在真實登入與正式資料環境驗收；v2 原倉退貨服務仍僅 demo-yushin Emulator。多倉完整前端、退款／折讓／抵用、自動產生來源單 backlink 與免費補送流程不在本批。

本機結果：Node 1,516／1,516 通過；本批預設CLOSE與歷史REPLACE重送兩項實際Emulator驗證通過。app及Functions共用產物一致性、JavaScript語法與差異格式檢查通過。未將未執行的真實登入前端驗收記為完成。
