# 直送到貨與倉庫缺貨投影一致化（2026-10-27）

## 問題與實證

原 Receiving Service 會透過共用 Fulfillment normalizer 正規化訂單品項。該 normalizer 對原廠直送仍以「訂購量－已履約－預留」推導倉庫缺貨，因此 5 件直送分批到貨 2 件時，會把 shortageQty 寫成 5，而不是不涉及倉庫的 0。

新增真實 Service 執行回歸先重現 5 !== 0；不是只比較原始碼文字。Workflow core 也會在只有 shortageQty 提示時反推不存在的直送倉庫預留，兩者應使用同一商業定義。

## 變更與操作

- 共用 Fulfillment normalizer：原廠直送的倉庫 shortageQty 為 0；倉庫商品沿原公式。已記錄的 reservedQty 仍保留供原交易驗證，不靠投影偷偷釋放預留事實。
- 共用 Workflow projection：不以直送的待送達量推導倉庫預留或缺貨。供應需求、已採購、實收到貨、未到貨、送達、退貨與工作分類仍用既有各自定義。
- 前後端由同一份核心產生，不逐頁加入補丁，不新增公式、欄位或操作。

正式環境尚未部署，原負責業務／工程師仍依原「確認直送到貨」操作；採購、倉管、管理員的角色範圍不變。本候選的新直送交易不再寫入錯誤的倉庫缺貨派生值；沒有資料遷移或直接修寫既有文件。

成功的到貨／送達累計照常增加；公司／分倉實貨、在途、批號、成本、預留及庫存異動保持不變。未到貨供應數量不是公司倉庫在途，兩者沒有混為同一個庫存指標。

## 驗證

- 共用 normalizer／workflow：分批、完成、退貨補送、缺少或殘留舊缺貨提示均不推導倉庫缺貨／預留；保留原供應與履約累計。倉庫商品仍依原公式。
- 原 Service：2＋3 件分批直送，部分及完成時 reservedQty、shortageQty 均為 0。
- 真 Auth → 實際匯出 Callable：業務／工程師與管理員確認後的實際 order.items 不含假缺貨，原 PO 憑證與重試驗證保留。
- 原 Chrome 1280／390px：分批到貨、成功回覆中斷／刷新原 ID 重試，核對實際保存的缺貨／預留為 0；物理庫存快照不變。
- 6／15 品項倉庫入庫與商品／服務混合回歸。
