# 固定角色與工作分工

2026-10-12 依公司實際分工確認；不新增行政角色，不要求兼任人員切換帳號。

| 角色 | 工作 | 不負責 |
|---|---|---|
| 業務 | 自己的 Forecast、估價單、客戶訂單、自行訂貨、送貨、核銷、取消未送餘量、申請退貨 | 採購確認、收貨、打單、庫存調整 |
| 採購 | 全公司採購需求、採購單／直接採購、成本、備貨、打單；兼收貨、出貨、退貨點收、調撥與盤點；代辦估價單與訂單 | 代業務確認送貨、核銷、取消客戶訂單或申請退貨 |
| 倉管 | 收貨、出貨、退貨點收、調撥寄出／點收、盤點 | 採購、成本維護、打單、客戶核銷 |
| 工程師 | 比照業務處理自己的維修料件估價、訂單、自行訂貨、送貨、核銷、取消與退貨；管理全公司儀器 | Forecast、代其他業務估價、採購確認、庫存調整 |
| 管理員 | 全部工作；帳號、固定角色、主檔、系統設定、分析與例外處理 | 不必參與每筆正常作業 |

## 採購與管理員代辦

- 估價單與訂單負責業務可選啟用中且有姓名與業務代碼的業務、工程師或管理員；未指定、停用、缺代號或非商業角色不可作為訂單負責業務。
- `ownerUid`、`salesCode`、`salesName` 是負責業務；`createdByUid`、`createdByName`、`createdByRole` 記錄實際建立人。
- 採購代建的訂單仍顯示在負責業務的清單，採購查看全公司資料。建立後不能藉一般編輯變更歸屬或建立人。
- 採購可載入並修改既有估價單；訂單沿用既有可編輯的交易方式、發票抬頭、備註、自行訂貨交易成本與交付資訊，不擴大成任意改品項或庫存事實。
- 送貨與核銷由負責業務追蹤。客戶取消／退貨由負責業務處理；採購負責供應商取消，並兼任貨品實際收貨。

## 寄貨與調撥

採購具有全部倉庫作業能力；未來倉管使用倉管角色即可，採購仍能代為執行。主倉自領不增加「已領貨」操作；寄給業務與直接寄客戶的出庫邏輯沿用既有寄貨流程。

## 本次驗證與發布

前端共用負責業務檢查，訂單下拉顯示角色；後端驗證負責業務的角色、啟用狀態與代號。測試涵蓋採購代建工程師訂單、負責業務查看、其他業務拒絕、錯誤代號／停用負責業務拒絕、禁止改歸屬／建立人，以及採購不得代為核銷、確認業務送貨或取消客戶訂單。

本次需更新前端及 `firestore.rules`，不需新增 Collection、Listener 或 Index。正式 Firebase 未登入，因此尚未部署規則；正式角色的手機／電腦端到端驗證仍待登入後執行。這是本次角色權限調整的測試範圍，不表示總驗收列出的其他安全或效能問題已全部修復。

驗證結果：860 項應用程式回歸測試、83 項 Firestore Emulator 測試全部通過；JavaScript 語法與差異空白檢查通過。採購不得藉「取消估價單成交」取消客戶訂單；已成交估價單仍可編輯內容，但採購不能解除成交。

## 2026-11-01 商務負責人補齊

- 固定角色不變。主管升任 admin 後，既有 UID、姓名、code、交付資料與歷史歸屬保留；空代碼的純管理帳號不列為新商務負責人。
- 新估價與訂單選人使用 UID，代碼由同一筆人員資料帶入；不依同名順序猜配。實際建立人另外記錄。採購不能代替負責人完成送貨、核銷等專屬確認。
- 工程師估價清單、取號、搜尋與 Rules 只認自己的歸屬；曾建立其他業務的估價單不再構成存取權。歷史文件不刪除，仍由原負責人與原有管理／採購範圍存取。
- 編輯舊估價保留原負責人與建立人欄位，包含原先未記錄的欄位；不補寫推測建立人。
- 儀器頁以 UID 選人、以實際代碼取號；原有儀器選項保留原歸屬，新表單不因同名而選錯人。工程師及業務的既有儀器工作範圍不變。
- 訂單／採購篩選原本已使用完整人員快取；Forecast、儀器及分析補齊有效管理員，歷史名稱仍可查。工程師不因此取得 Forecast。

- 既有業務代碼交接仍依正式代碼授權相容舊單據；不把顯示姓名作為權限。沒有遷移歷史 ownerUid，也未更動實際帳號代碼。
- 產品頁新增正式主檔與既有維護分開授權；業務不能編輯、停用、刪除既有主檔或維護成本。建立本身不寫入任何庫存／需求。
