# 商業流程稽核與續修清單（2026-10-14）

基準 main：`3d72400`。使用者確認正式專案 `yu-shing-company` 為 Firestore Standard，並授權本次修正推送、合併 main；未授權執行歷史資料刪除或重大資料遷移。正式 Firebase CLI 尚未登入，不部署、不改正式交易資料。

**本文件不是全面驗收合格證明。** 新訂單跨倉分配、同品項多地點分批交付、舊資料修復與完整五角色正式站驗收仍未結案。

## 數量與權威來源

| 數量／狀態 | 定義及來源 |
|---|---|
| 訂購量 | orders.items 的客戶承諾量，不能因採購或调撥而增加 |
| 有效交付 | deliveryRecords 的累計送貨，扣除需要補送的退貨；保留歷史事件，不截斷累計量 |
| 尚待交付 | 訂購量減有效交付 |
| 現有量 | inventory／warehouseStocks 的實體帳；調撥途中另記，目的倉未點收前不能出貨 |
| 預留量 | inventoryReservations.quantity，同交易更新公司／分倉 reserved 與庫存憑證 |
| 實貨缺口 | 尚待交付減目前預留；不是尚未採購量 |
| 已下訂待到貨 | supplyOrderedQty 減 receivedQty，由供應事件累計；不能再次被現貨覆蓋同一缺口 |
| 待採購 | 實貨缺口扣除已下訂待到貨，最小為零；採購需求是投影，不是另一份庫存真相 |
| 收貨 | supplyOrders + receipts + lots + inventory + source item 同交易；直送不碰公司庫存 |
| 調撥收貨 | stockTransfers + 公司途中量 + 目的倉／批次同交易，不增加公司總量 |
| 倉庫交付業務 | 訂單預留移入業務保管位置，不能直接當作已送客戶 |
| 已寄客戶 | 沿用既定規則同步登錄送貨，不代表客戶簽收證明 |
| 核銷 | 單據核銷，非收款或發票開立 |

## 已修正及清理

| 問題 | 本批修正 | 驗證範圍 |
|---|---|---|
| 補貨分配後採購需求仍保留舊數量 | 同一交易更新訂單、預留、公司／分倉 reserved、需求及分配進度 | 實際函式合成資料；包含失敗整筆不提交、累計到貨歷史保留與重試 |
| 補貨再次覆蓋已下訂供應 | 只分配尚未被供應承諾涵蓋的缺口 | 未到貨 2／5 等邊界測試 |
| 同步重試再次預留已下訂需求 | 共用 reservation-core 扣除 inTransitQty，保留實貨缺口語意 | 同品項預留重試、純核心測試 |
| 恢復訂單的 shortageQty 使用另一套定義 | 改為尚待交付减預留；採購缺口仍交共用 workflow 計算 | 既有生命週期回歸 |
| 備貨調撥只增加主倉庫存 | 收貨後使用同一分配函式；進度寫在 stockTransfers，失敗可從同筆待分配重試 | 原子調撥、批次不重複建立、分配失敗後重試、checkpoint 規則 |
| 直送由採購／倉管確認 | 訂單負責業務／工程師在訂單按「確認直送到貨」；管理員保留例外處理 | 實際收貨函式搭配 Emulator，部分直送與重試、其他角色拒絕 |
| 直送需要讀正式採購成本 | 使用 receivingSupplyOrders 的去成本投影，查詢限 ownerUid + orderId + itemId + DIRECT_SHIP | 精確查詢與非本人讀取拒絕、正式供應成本仍禁止讀取 |
| 工程師無法重試自己的訂單 | 使用 exact ownerUid；不能以 createdByUid 接管別人的訂單 | 五角色／歸屬測試 |
| 快速建產品後產品頁沒有更新 | 主檔編輯與快速建立共用畫面／快取同步 | 失效舊搜尋、解除讀取中狀態、結果去重 |
| 查重兩套實作且各只看 20 筆 | 共用 exact-code 50 筆分頁查重，含停用產品；快速建檔不得使用停用主檔 | 第 51 筆同廠牌查重、原回歸 |
| 快速建檔可能覆盖同時建立的同 ID 主檔 | 交易中確認文件不存在，存在時要求重查，不 merge 覆盖 | 保存交易行為測試；跨不同格式 ID 的唯一性仍見未結案 |
| 規則探測失敗回退另一套無憑證寫入 | runRoleTransaction 一律使用共用 StockPermissions，不回退裸 transaction | 共用交易及去成本投影回歸 |

未新增 Collection、Listener 或 CSS 主色；正式 PDF 與列印格式未改。新增讀取限於查重下一頁、分配交易的單筆需求、使用者按直送確認，以及倉庫的待分配調撥清單。沒有全歷史 Listener。

## 清理後保留的核心

- 數量／待採購：workflow-core + procurement-demand-core（不同文件的必要投影，不是兩份獨立採購事實）。
- 預留：reservation-core；發貨數量：fulfillment-core；實體庫存／批次：inventory-core。
- 實際寫入與安全憑證：StockPermissions；普通收貨與直送共用 receiveSupplyOrderRecord。
- 補貨和備貨調撥共用 allocateFreeReceiptStockToShortages；僅 checkpoint 來源不同。
- 產品查重：findDuplicateProductMaster；產品保存後畫面更新：syncSavedProductMaster。

## 未結案：不能在回報中省略

| 項目 | 實際缺口／下一步 |
|---|---|
| 新訂單跨倉自動分配 | orderWarehouse 已隱藏，但仍帶預設單倉；reserveSingleOrderItem 還未實作多倉配置。本批沒有把這項宣稱解決。 |
| 同品項分散於多倉／業務保管位置 | 現行 item.warehouseId + 一筆 reservation 只表示一個位置；必須先統一數量級位置模型，再改各轉單、收貨、發貨、取消、退貨與 Rules。不能只選庫存最多的倉就稱多倉完成。 |
| 分批交給業務／訂單調撥 | 現行需該品項剩餘數量全部到齊、預留並打單。限制避免後續供應混入別的位置，未直接解除。需與多地點模型一同處理。 |
| 初始化／來源轉單及同步中斷 | 仍有建立訂單→逐項預留→需求→自購→來源文件的多階段流程；pending/failed 及同 ID 重試可恢復，但 full-item 快照回填與 batch 需求仍需交易級競態驗證。 |
| 動態需求持久化 | 初始 persistOrderProcurementDemands、取消／恢復及其他庫存釋放仍需逐入口檢查；本批收貨分配原子同步不代表所有入口皆已同步。 |
| 自由庫存釋放 | 取消、盤點增加或退貨轉自由庫存後，尚無一個全面覆蓋所有入口的可恢復分配機制。 |
| 大量缺貨分配 | 候選查詢目前每狀態先查最多 500 筆，再前端排序；跨頁最早優先及大量讀取仍需改進。 |
| 主檔身份唯一性 | 共用查重解決分頁與同 ID 覆盖；不同符號格式／廠牌別名產生不同 document ID 的併發唯一性仍需統一索引或 ID 策略，不能任意重寫歷史 productId。 |
| 歷史不一致資料 | 沒有執行正式庫存、需求或主檔修復；新程式不會自動修復之前已產生的所有錯誤。需先備份、唯讀差異預覽與核准的修復交易。 |
| 更廣泛安全規則 | 商務品項投影的防偽、一般收貨憑證欄位上限／跨文件驗證、個人資料與人員名錄分離仍需續查。既有 users 文件可被其他 active 成員讀取，含聯絡資料的情況尚未處理。 |
| 正式設定與操作 | 未登入正式 Firebase；Rules 發布、索引狀態與五角色正式資料端到端驗收未執行。 |
