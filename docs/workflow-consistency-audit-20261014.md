## 數量與權威來源

| 數量／狀態 | 定義及來源 |
|---|---|
| 訂購量 | orders.items 的客戶承諾量，不能因採購或调撥而增加 |
| 有效交付 | deliveryRecords 的累計送貨，扣除需要補送的退貨；保留歷史事件，不截斷累計量 |
| 尚待交付 | 訂購量減有效交付 |
| 現有量 | inventory／warehouseStocks 的實體帳；調撥途中另記，目的倉未點收前不能出貨 |
| 預留量 | inventoryReservations.quantity，同交易更新公司／分倉 reserved 與庫存憑證 |
| 實貨缺口 | 尚待交付減目前預留；不是尚未採購量 |
| 已下訂待到貨 | supplyOrderedQty 減 receivedQty，由供應事件累計；不能再次被現貨覆蓋同一缺口 |
| 待採購 | 實貨缺口扣除已下訂待到貨，最小為零；採購需求是投影，不是另一份庫存真相 |
| 收貨 | supplyOrders + receipts + lots + inventory + source item 同交易；直送不碰公司庫存 |
| 調撥收貨 | stockTransfers + 公司途中量 + 目的倉／批次同交易，不增加公司總量 |
| 倉庫交付業務 | 訂單預留移入業務保管位置，不能直接當作已送客戶 |
| 已寄客戶 | 沿用既定規則同步登錄送貨，不代表客戶簽收證明 |
| 核銷 | 單據核銷，非收款或發票開立 |

## 清理後保留的核心

- 數量／待採購：workflow-core + procurement-demand-core（不同文件的必要投影，不是兩份獨立採購事實）。
- 預留：reservation-core；發貨數量：fulfillment-core；實體庫存／批次：inventory-core。
- 實際寫入與安全憑證：StockPermissions；普通收貨與直送共用 receiveSupplyOrderRecord。
- 補貨和備貨調撥共用 allocateFreeReceiptStockToShortages；僅 checkpoint 來源不同。
- 產品查重：findDuplicateProductMaster；產品保存後畫面更新：syncSavedProductMaster。

## 第二批：建單預留與採購需求一致性

基準 main：`6337c124`（PR #66）。本批仍不是跨倉自動分配的實作，也沒有部署正式 Firebase。

| 原因與影響 | 修正／清理 |
|---|---|
| 預留交易使用呼叫端舊品項，最後再整份回寫；並行重試可能抹掉較新的採購、收貨或其他品項資料 | 每次交易重讀正式訂單，依 itemId 尋找最新品項，原子更新該品項、預留與公司／分倉 reserved；移除最後整份 reservedItems 回寫 |
| 預留與需求分開提交，部分成功時兩者不一致 | 同一品項的需求與預留共用同筆交易；多品項維持逐筆原子處理，利用原有 pending／failed 與固定文件 ID 重試，不增加 Collection |
| 庫存全覆蓋時跳過需求寫入，留下舊待採購量 | 不建立新的零量需求，但既有需求必須更新為最新零缺口，保留供應累計、需求日期和建立日期 |
| 取消需求先讀快照再 batch，可能覆蓋較新的供應進度；舊取消訊息也可能覆蓋恢復後的訂單 | 取消與恢復使用同一最新來源交易投影，取消保留當下已下訂及已到貨數量；不信任呼叫端 lifecycleStatus |
| 只看分倉可用量，公司帳缺失仍可能預留 | 公司與分倉帳共同限制新增预留；既有預留缺少對應庫存時停止，不能自動修復歷史帳 |
| 同交易加入來源與需求後，重複 Rules 憑證驗證超過運算上限 | 共用來源驗證只執行一次；庫存文件驗證同交易新建的不可變 stockOperations，憑證本身由 create 規則完整驗證。保留 actor、來源、產品、位置、數量與新建要求 |
| 同步重試出現新庫存時，業務無權同步降低既有需求 | 限本人 pending／failed 的倉庫品項，需來源品項、預留與供應累計吻合，才准調整需求；不能藉此變更供應事實。倉管不可接管未完成的建單初始化 |

共用核心仍是 reservation-core、workflow-core、procurement-demand-core、fulfillment-core 與 StockPermissions；新增 orderItemProcurementDemandDocument 作為建單及生命週期需求投影入口。移除單品項／多品項兩條獨立回寫流程、兩套 lifecycle batch 與未使用的新 directShipQty 欄位写入；歷史欄位與交易資料未刪除。

新增行為驗收包含：同品項多列、並行重試、供應紀錄在交易重試間更新、另一品項與備註不被覆蓋、取消／作廢、已完成來源、全庫存覆蓋、直送不碰庫存、缺公司帳、舊供應投影不一致時整筆拒絕、原有單倉換倉釋放。兩項舊替身測試移入這些較完整的交易行為測試。

本機靜態語法與 diff 檢查通過；947 項應用測試、111 項 Firestore Emulator 測試通過。實際函式搭配 Emulator 涵蓋業務、工程師、採購代建與管理員的一般／直送初始化及重試，倉管與其他負責業務不得接管；新增現貨降低需求的合法交易與偽造數量拒絕均通過。

瀏覽器：本機 Chromium 仍受既有執行環境限制，本批不聲稱本機瀏覽器通過；GitHub CI 完成後另外記錄結果。正式資料未修復、Rules／Index／Hosting／Functions 未部署。沒有新增查詢索引或 Listener；增加單筆來源及需求交易讀取、同步前後單張訂單讀取，避免重新載入全清單。

## 第三批：同步結果的競態與重新載入恢復

基準 main：`e1d104a`（PR #67）。三個入口原本各自直接寫 completed／failed；舊工作的網路錯誤可能讓另一個已完成的訂單倒退為 failed，舊成功也可能蓋掉較新的失敗原因。

新增 synchronizeOrderInventory 共用協調入口，writeOrderInventorySyncState 使用單張訂單交易讀取最新狀態及 inventoryReservationAttemptId。每次開始輪替識別碼，完成或失敗只能使用同一識別碼；已完成與已取消／作廢不接受舊回呼修改。識別碼寫在既有 orders 文件，不新增 Collection、Listener 或 Index，重新載入後可從該筆訂單重試。

取消三個入口各自的同步結果 set 與重複 catch 寫入；結果交易同時用最新品項重算 workCategories，避免完成時留下過期工作分類。Forecast 同步沿用轉單開始時的登入 UID，換帳號後不接續原工作。保留原有逐項原子预留、固定供應識別碼與歷史交易，不增加業務操作。

Rules 同步限制狀態轉換、識別碼及錯誤文字長度，完成不能倒退，過期識別碼及取消來源不能寫結果，倉管與其他負責業務不可接管。規則仍為待正式環境驗證的原型；這個狀態保護不能替代所有履約與供應憑證稽核。

本機靜態檢查與 958 項應用測試通過，新增驗收含舊失敗／新成功、舊成功／新失敗、完成已提交但回覆遺失、開始回覆遺失後重新載入、取消或作廢、交易衝突、換帳號、角色拒絕與持久化錯誤。已新增實際共享流程 Emulator 測試及跨角色狀態偽造測試；本機工具快取在此工作階段已不可用，重新取得工具未完成，故本批本機 Emulator 尚未執行。

第三批 PR #68 已合併 main `c35d2aa`；最終 CI run 38530636801 全數成功，958 項應用及 113 項 Emulator 通過，電腦／手機共用介面、建單與五角色直送 fixture 通過。第一輪一項舊測試仍沿用無識別碼寫入，已更新成缺識別碼拒絕、有新識別碼合法重試；沒有放寬新防護。瀏覽器仍使用隔離資料，正式環境未驗證。

正式 Firebase 未部署；本批需發布 Rules，無 Index 變更。跨倉分配、多地點分批交付、来源估價單／Forecast 的失敗進度持久化及其他庫存釋放入口仍未結案。

## 第四批：移除重複回歸工作流程

main 原本同時執行 regression-tests.yml 與 regression.yml，兩者重複跑 Node 語法與相同應用測試。查核文件、測試與其他工作流程，未發現舊檔路徑的呼叫依賴。保留完整 regression.yml，併入舊流程的手動觸發、唯讀 contents 權限及 customer-cancellations 語法檢查；加入按 PR／branch 分組的 concurrency，只停止同一組較舊的回歸執行，保留各 PR 各自驗證。

刪除被完整流程涵蓋的 regression-tests.yml，沒有關閉 Node、電腦／手機或 Emulator 測試，也沒有修改產品介面或交易資料。YAML 結構與觸發條件已解析檢查，完整流程執行結果須以本批 CI 記錄為準。這批是驗證流程清理，不代表所有前端商業重複逻輯都已清除。

## 第五批：來源文件同步進度與恢復

基準 main：`0328a7f`。原本庫存完成後，估價單更新失敗只留在當次回呼，訂單完成後就沒有重試入口；Forecast 回寫甚至未 await，可能在來源尚未更新時就呈現整體成功。

共用 syncNewOrderSourceDocuments 改為交易重讀最新訂單與來源，來源估價單成交／關聯或 Forecast 關聯，與 orders.sourceDocumentSyncStatus 完成記錄同筆提交。失敗另在同一訂單保存有長度限制的 error 與更新時間；重試沿用既有控制，只重做未完成的來源階段，不重複預留。完成回覆遺失可讀取持久化結果，不倒退成失敗、不增加重複關聯。來源缺失不再使用 set/merge 重建空來源，取消／作廢及換帳號停止更新。

新建有來源訂單保存 pending；直接 Forecast 轉單原本就將新單與來源關聯一起 batch 提交，保存 completed 反映這個事實。正常新建與轉單仍走既有入口，未新增 Collection、Listener 或 Index。Rules 限制來源身份及進度寫入，完成需要真正的來源關聯與估價單成交證據，新建也不能直接偽造 completed；保留既定 Forecast 讀寫角色，不擴大採購或工程師的 Forecast 存取。

移除估價單與 Forecast 兩條獨立 merge 回寫／未等待回呼，改用同一原子來源流程。庫存同步、来源同步仍是不同必要階段，各自的持久化進度不能被另一階段覆蓋。同步完畢的庫存仍沿用第三批共用核心，正式 PDF 與配色未修改。

本機 968 項應用測試、語法及 diff 檢查通過；新增 10 項來源交易行為驗收。增加 Emulator 的實際 quote／Forecast 來源交易、歸屬拒絕與新建完成防偽驗收，並擴充既有 Chrome fixture，檢查五角色／電腦／手機來源重試只執行來源階段。Emulator 與瀏覽器以 CI 最終結果補登；本批本機未執行這兩類驗收，正式環境未測試或部署。

## 第六批：單一庫存位置的自動選倉與錯誤缺口保護

基準 main：`619ea76`。此批不是完整多倉合併與多地點交付；目前每個 itemId 仍只有一個 reservation 與 warehouseId，不能把多倉總數直接寫成某一倉的可出貨量。

| 情境／影響 | 修正與驗收 |
|---|---|
| 預設倉無貨，其他一倉足量，原本誤判全數待採購 | reservation-core 共用選倉，在同一預留交易重讀所有候選分倉及倉庫主檔，配置整個品項至能供應的倉。訂單、預留、公司／分倉 reserved 與需求同筆提交；onHand 不變 |
| 只有另一個倉有部分現貨 | 配置至該唯一有可用現貨的倉，只將公司真正缺口列入採購；後續採購入庫沿用這個位置 |
| 預設倉可供應，其他倉更多 | 保留既有提示位置，不以最大庫存作為每次強制換倉依據。其他足量候選依預設倉與固定 ID 排序，並行交易重讀後重算 |
| 多倉各有部分現貨、必須合併才可覆蓋 | 未完成多位置模型；停止此品項交易，保留原有 pending／failed 恢復機制，避免新建錯誤採購需求。該訂單需完成庫存配置後才可採購或交付。這是暫時阻擋，不能視為需求已解決 |
| 已有預留、採購、收貨、打單、送貨、退貨或交給業務的品項 | 不自動換倉；包含從權威送退貨紀錄取得的進度。保留既有位置及供應承諾，避免後續到貨被放到別處 |
| 初次缺貨寫入零量預留，重試時另一倉有貨 | 允許本人未完成同步的零量、無履約承諾品項，透過同交易證據更換位置及需求位置；既有正數預留、已完成、停用倉及保管位置不能使用此例外 |
| 倉庫主檔快取過期或前 50 筆包含大量保管位置 | 倉庫品項的新建同步強制更新主檔，使用既有分頁讀取，不再只截取前 50 筆；交易仍驗證即時 active。讀取失敗停止，不以舊快取宣告完成。全直送單不查倉庫主檔 |
| 直接 API 建採購繞過前端同步限制 | 有 orderId 的 PURCHASING_PO／PURCHASING_MANUAL 新供應必須有正常且非 pending／failed 的來源訂單；保留無客戶來源的補貨與既有初始化自行訂货流程。完整供應憑證安全稽核仍未完成 |

共用核心為既有 reservation-core 的 reservationLocationCanChange、selectSingleWarehouse 及 planReservation，所有建單／估價成交／Forecast／重試入口仍使用 reserveSingleOrderItem。移除原有「隱藏欄位等於正式選倉」假設與倉庫主檔的前 50 筆截斷，不增設另一套預留寫入、Collection、Listener、Index、角色或 PDF 格式。必要增加各候選倉庫主檔及分倉的交易讀取。

本機語法、diff 與 983 項應用測試通過，新增 15 項交易情境。涵蓋單一遠端倉全量／部分、同品項多列、不同訂單並行、即時停用、供應／履約鎖定、零量恢復、換帳號與失敗不部分寫入；以实际函式連接備貨打單數量、調回主倉、途中拒絕出貨、重複點收及批次扣庫存。該串接在隔離交易替身執行，不能當成正式五角色端到端驗收。啟始 UID 傳到各品項預留及初始化自行訂貨，主檔更新、供應讀取或兩品項之間換帳號都停止下一筆寫入；已提交原帳號的交易仍保留，可用固定識別碼恢復。另加 Emulator 的實際四角色選倉／零量重試、異常分散庫存與規則拒絕、未同步來源供應防繞過及共用讀取權限矩陣。CI 最終 Emulator／Chrome 結果需另行記錄，本批本機未執行兩者。

CI 前兩輪定位到跨倉交易的 Rules 重複運算，以及採購原有品項欄位白名單不允許初始化選倉。Rules 共用固定角色／庫存讀取判斷，單一預留憑證不再呼叫其餘四個空欄位的 delta 計算；仍保留多預留的完整累計證據。採購初始化更換位置限正常未完成來源、單一改變品項、沒有既有供應／履約，以及同交易 reservation 與啟用非保管倉，未將 warehouseId 加入一般採購修改白名單。

## 第七批：補貨候選分頁與重複排序清理

基準 main：`93e278c`。補貨及自由調撥到貨原本最多讀每種狀態前 500 筆，再在瀏覽器排序；這個結果按文件 ID 分頁，不是按訂單日期分頁。第 501 筆之後可能有更早的有效需求，也可能前 500 筆都在其他倉，因此不能據此判定沒有待分配訂單。

移除 500 筆截斷，沿用每次 50 筆與既有 productKey／status 查詢，逐頁比較只保留該狀態最早的合格候選，再比較 shortage／active。每筆成功交易後仍重讀候選並重讀訂單、預留、公司／分倉、需求及持久化到貨進度，避免累計超配或把已下訂待到貨重複覆蓋。分頁失敗或游標未前進會停止，不將不完整搜尋宣告完成；原有收貨／調撥 checkpoint 可安全重試。

兩套日期／訂單排序改用 reservation-core.compareReservationPriority：日期、orderId、itemId、實際文件 ID。保留缺日期排在末端的歷史相容，不用新增 orderBy 造成缺欄位舊資料被 Firestore 排除。讀取的 ID 以 snapshot.id 為準，舊文件內誤存 id 不會導向另一筆預留。移除各頁候選陣列重複排序、去重掃描與核心未使用的 __index 複製；沒有移除交易、供應歷史或實際數量欄位。

本機語法、diff 與 990 項應用測試通過，新增 7 項行為驗收，包含超過 500 筆且最舊在後頁、兩狀態比較、同日訂單／品項優先、取消候選不阻塞、文件內錯誤 id、後頁斷線重試及游標重複。新增 Emulator 的實際採購／倉管各執行 550 筆候選、原子分配及到貨 checkpoint 重試；結果需以本批 CI 記錄為準，本機 Emulator／Chrome 未執行，正式資料未讀寫或測試。

本批沒有 Rules、Index、Collection、Listener、角色、樣式或 PDF 變更，不需因本批新增 Firebase 設定。完整扫描對單次候選使用固定記憶體，但讀取成本會隨該產品待預留與已預留文件數增加；沒有用任意截斷換取較少讀取。未將這個修正稱為全面 FIFO 併發認證或所有庫存釋放入口已覆蓋。第六批 Rules 仍需另行發布，使用者先前只回報較早 Rules 更新，正式部署 SHA 尚未独立核验。
