# 隔離後端收貨：6–15 品項來源（2026-10-27）

追蹤 #308、#291。前置為 #310 的共用履約投影與 #312 的交易預算；Preview 匯出另由 #309 處理。

## 本批範圍

同一個 `receiveV2Supply` 後端 adapter 與 Receiving Service 處理正常、已完成 v2 初始化的 1–15 品項實體入庫來源。可含 SERVICE 品項，服務工作不得建立庫存或供應。沿用整單履約來源、所有實體品項的商品／預留、兩倉帳與 PO 原憑證查核，不建立另一套數量計算。

只有 dependency-bound 後端 runtime 明確設定 `receivingSourceItemLimit:15`。舊 client Service 預設仍為 5；Callable 不接受使用者傳入上限。直送入口仍限定 1–5，含直送的實體入庫混合來源仍拒絕，須另批完成直送契約及證據驗收後才開放。其他採購、初始化、打單、出貨、送達與生命週期入口沒有跟著放寬。

一般角色操作尚未正式改變。成功入庫沿原交易同時增加實貨與來源預留、減少在途和缺口、更新供應／需求實收，建立 receipt、lot、受保護成本及庫存異動；同品項其他列與服務工作不變。來源或權限不符整筆不寫，沿用原操作 ID 可重試。

## 本機驗證與適用界線

新增 `tests/emulator-receiving-fifteen.cjs`，納入完整 CI runner；`--suite=receiving` 僅供本機定向迭代，不能代替完整 CI。

來源初始化、採購單、在途及需求由 Admin fixture 準備，刻意避開仍限定 5 品項的其他 writer。實際收貨走 Auth SDK → Callable SDK → 後端 → Firestore Emulator，不能宣稱建單／採購／收貨原站端到端 15 品項全部完成。

固定驗收：
- 6 與 15 品項、同商品多列、兩倉、首末列分批收貨；重複送出及成功結果丟棄後原 ID 重送。
- 最後餘量兩個請求競爭只成功一次；公司／分倉實貨、預留、在途、來源缺口、需求、批號與成本一致。
- 非選取品項來源損壞、重複識別碼、直送混入、超收、第 16 品項、業務／工程師越權與即時停用，失敗後無部分寫入。
- 採購／倉管經 Callable 成功；管理員的 14 個不同商品加 1 個服務來源另以實際後端 transaction 量測每次 attempt 讀寫，原服務品項與案件不變。後續仍須原站桌機／手機及 Preview 實際驗收。

本機一般測試、Emulator 最終結果及交易量測數字記錄於 PR。完整 CI 為獨立關卡；未通過前不合併。未部署 Firebase、未啟用正式旗標、未修改正式資料，無 Rules／Index 更新；本批不刪舊 client writer。
