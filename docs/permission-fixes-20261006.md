# 角色權限修正與部署（2026-10-06）

## 本次修正

- 業務、工程師的庫存修改必須伴隨自己訂單的占用紀錄和新的庫存異動紀錄；不能只呼叫 API 改庫存數字。
- 採購、倉管只能修改訂單品項的作業欄位，不能透過整包 items 改品名、料號、數量或售價。
- 商品查詢頁保留合法的估價選取與採購主檔操作，由各操作本身檢查權限。
- 工程師可以查詢、搜尋、載入和複製自己代建的估價單；成交建單仍交由負責業務。
- 永久刪除訂單只限管理員；停用帳號的 disabled 標記也由後端檢查。
- 業務、工程師可唯讀查看庫存，不能做入庫、收貨或政策設定。
- 倉管讀取不含公司進貨成本的 receivingSupplyOrders。正式 supplyOrders、purchaseOrders 只供管理員、採購讀取。
- 倉管收貨的批次成本只記錄來源供應單 ID；庫存分析由有成本權限的角色讀取實際成本。

## 尚需部署 Firebase

GitHub Pages 更新不會部署 Firestore 規則或索引。本次執行環境沒有 Firebase 登入授權，未部署正式 Firebase。

由有 yu-shing-company 專案部署權限的帳號，在此 repo 執行：

```sh
firebase login
firebase deploy --project yu-shing-company --only firestore:rules,firestore:indexes
```

確認索引完成建立後重新登入網站。前端會探測新規則；確認前仍使用舊交易流程，且不開放業務、工程師的新庫存分頁。因此後端權限收緊與成本隔離，在部署前不能視為已生效。

新規則部署後，請管理員或採購先開啟待收貨頁，系統會從既有待收貨供應單同步不含成本的收貨檢視。倉管再重新整理；新建及後續異動的供應單會在同一交易同步收貨檢視。此步驟只建立衍生檢視，不增加收貨或改變庫存。

## 運算限制與驗證範圍

- Firestore Rules 無法迭代陣列且有運算上限：採購、倉管修改 items 的訂單目前最多 30 個品項；更大的訂單由管理員處理。items 未變的其他合法更新不受此項限制。
- 業務、工程師同次庫存交易、同商品的占用紀錄最多 5 筆；超過時明確拒絕並交由管理員處理。
- 已驗證純 Node 回歸及 Firestore 模擬器的允許／拒絕案例，包含多品項占用、出貨、還原與退貨。不宣稱覆蓋所有惡意組合或所有並行業務情境。
- 正式網站可開啟，但只有登入畫面，沒有各角色的登入狀態；尚未進行各角色的桌機／手機完整實測，也沒有在正式資料上測試收貨或庫存修改。
