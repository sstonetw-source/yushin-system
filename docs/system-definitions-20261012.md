# 系統用語與判斷

| 用語 | 統一定義 |
|---|---|
| 正常訂單 | 未取消或作廢；建立時儲存 `status: active`。前端履約判斷使用 `normal` 作為正常的計算結果，而非要求資料中的 status 等於 normal。 |
| 取消／作廢 | `status` 或 `orderStatus` 任一為 cancelled／voided，就停止履約。已送貨的部分保留紀錄；不能重新預留庫存。 |
| 保留採購轉庫存 | 客戶取消後，由採購確認供應商無法取消，設定 KEEP_STOCK；貨到仍入庫，來源已取消訂單不重新預留。 |
| 需求日期 | 採購需求自己的需要日期。收貨只推進數量與進度，不以供應商交期覆蓋。 |
| 預計到貨日 | 供應商預計交貨日期，存於 supplyOrders；與需求日期分開。 |
| 負責業務 | 文件或訂單的歸屬人，可以是業務或工程師。採購代辦不改變負責業務。使用者角色與操作權限維持既定分工。 |
| 核銷 | 完成單據核銷，仍使用現有的一次核銷操作；不代表款項入帳或發票開立。 |
| 核銷日期 | `billingDate`，由核銷時寫入及後續補登；畫面、歷程與匯出使用同一名稱。未新增收款或開票流程。 |
| 已出貨 | 倉庫已將實體貨寄出或交付。 |
| 已送貨 | 既有送貨流程的登錄結果。直接寄客戶的倉庫出貨會同步登錄送貨，顯示「已送貨（已寄客戶）」，不代表物流簽收證明。 |
| 已寄負責業務・待送客戶 | 已移交負責業務保管並保留訂單預留，負責業務送達後才登錄已送貨。 |

Firestore 中收貨、預留、取消處置、交付設定、出貨與調撥共用 `orderIsCancelled`，與前端 `normalizedOrderStatus` 的定義一致。既有供應狀態與採購需求狀態屬於不同文件，各自保留原本的枚舉及數量語意；物流模式及操作事件識別碼維持原協定。

核銷欄位改名為 billingDate，不執行舊資料批量改寫或加入 invoiceDate 相容分支。前端與 Firebase Rules 必須一起發布，否則採購對新日期欄位的修改可能被舊規則拒絕。

驗證涵蓋雙狀態欄位互相矛盾時的取消／作廢處理、管理員／採購／倉管／業務的預留防護、採購 KEEP_STOCK 權限、三種收貨角色的原子收貨與重試、需求日與供應商交期分離、核銷與完成日期、直接寄客戶及負責業務保管的顯示。

驗證結果：863 項應用程式測試、89 項 Firestore Emulator 規則測試通過。正式 Firebase 尚無部署憑證，線上規則發布與登入後實測仍待完成。
