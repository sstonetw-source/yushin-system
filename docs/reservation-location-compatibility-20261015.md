# 多位置啟用前的交易相容性保護

基準 main：`4f7b6c42111fa496794351b25e4cc86a073b8059`。接續 PR #78／#79 的純位置模型與 PR #80 的舊 PR 整理。本批是現行交易的相容性保護，**尚未啟用多倉預留、各倉分批出貨或多位置業務領貨**。

## 實際風險

目前 live 預留、收貨、送貨、取消與調撥仍使用 `inventoryReservations.quantity + warehouseId`。`stock-permissions.js` 產生的公司／分倉差額證據，以及 Rules 中對應驗證，也依整筆 quantity 代表單一倉。直接把位置陣列寫入正式預留，再讓舊入口處理，可能把全部數量扣到某一倉或覆寫位置帳。

現行來源驗證原本不限制尚未啟用的位置欄位；因此「目前前端沒有產生新版資料」不能代替資料庫保護。管理員用戶端也不應提前將尚未支援的模型當成可作業資料。

## 本批變更

| 層級 | 保護 |
|---|---|
| 共用交易讀取 | `StockPermissions.run` 讀到預留含 locationSchemaVersion、locations、allocations 或 warehouseAllocations 時，停止該交易，不讓舊回呼使用整筆 quantity 扣庫存 |
| 共用交易寫入 | set／update 的上述欄位及點號欄位路徑都停止；空陣列、null、版本 0 或未知版本也不能當成沒有位置資料 |
| 未先讀取就覆寫 | 在補來源歸屬與產生憑證前，先讀該預留；若原文件含未支援欄位，就算新 payload 刪光這些欄位也停止，不能掩蓋原帳。已有交易讀取會重用，不重複查詢 |
| Firestore create | 正式用戶端不得加入未啟用位置欄位，包含管理員與可合法產生庫存證據的採購／倉管 |
| Firestore update | 新值與舊值都必須為現有單倉格式；不能用整份 set 將舊位置欄位移除後繞過。檢查與原來源／歸屬／數量／憑證驗證同時成立 |
| 唯讀核對 | Rules 的 get／list 權限不改；有權人員仍可唯讀稽核。刪除與後端特權權限不擴大，也沒有執行資料刪除或修復 |

判斷只限 inventoryReservations 集合，不誤擋收貨、批次或其他集合中的 allocations。舊單的一般數量、小數數量、零量預留與業務保管 warehouseId 沿用原語意；沒有自動升版、轉譯後回寫或加入第二份庫存帳。

錯誤訊息帶來源訂單／貨號或品項，說明已停止作業、保留原資料並由管理員核對，不引導使用者直接改庫存或重複建單。前端在原錯誤回饋顯示此訊息；後端尚未成功不會回報完成。

## 讀取與權限

沒有新增 Query、Collection、Listener 或 Index。正常已讀取預留的作業沿用該 snapshot；原本未先讀預留的寫入，每個不同預留多一筆必要交易讀取，以阻止覆寫未支援資料。來源訂單歸屬與 item index 仍由同一交易重讀，未取消原有身份／角色與提交前檢查。

Rules 只增加文件欄位存在檢查，不新增跨文件 get。固定五角色、成本權限、庫存數量、PDF 排版與 UI 配色不改。

## 驗證

- 本機語法、diff 與 1,062 項應用回歸通過。
- 新增六項共用交易行為測試：五角色未知格式讀取、set／update／點號路徑、未讀覆寫、排入寫入佇列後 payload 被改動、一般小數／保管位置相容與其他集合不誤擋。多筆已緩衝的寫入遇錯都不提交。
- 新增三項 Emulator 測試：合法庫存證據仍不可加位置欄位、業務／工程師繞過 JavaScript 防護後原生寫入被 Rules 拒絕、舊資料位置欄位不能被剝除覆寫且整個 batch 不部分提交。各組同時保留合法單倉流程可成功的對照。
- 桌面／手機及完整 Emulator 以本批 PR 的最終 CI 為準；本機未跑 Chrome 或 Emulator，沒有正式資料驗收。

## 發布與下一步

本批需發布 firestore.rules，才有直接 API 防繞過保護；沒有新 Index。前端更新 stock-permissions.js 與應用資源版本為 20261015-2。未執行正式 Firebase 發布，未查核已部署規則 SHA，也未批量修改歷史資料。

後續仍須依 multi-location-reservation-model-20261015.md 的接線矩陣，同批改造預留、收貨、各倉實際出貨、取消／恢復、退貨、調撥、業務保管、位置差額憑證及 Rules，並用真實函式 Emulator 驗證後，才可逐項解除本相容性限制。不能為了讓新版資料寫入成功，單獨拿掉此保護或只放寬規則。
