# 收貨後端交易預算前置作業（2026-10-27）

追蹤：#291、#308。此批只補實際收貨後端 adapter 的讀寫預算，沒有開放 15 品項。

## 實際變更

- `receiveV2Supply` 沿用現有 Receiving Service 和 Firestore 原子交易。
- 每次 Firestore transaction attempt 分別限制：100 個讀取請求、400 份讀取文件、100 個寫入操作。這是本功能的保守上限，不是 Firestore 平台限制。
- 同一文件（含不存在的文件）的重讀沿用同一 Promise；查詢結果按實際文件數計入，空查詢仍占一次請求。所有額外的去成本供應投影與混合服務工作索引寫入也計入。
- 所有寫入保留到最後；超量、讀取失敗或讀取尚未完成時禁止提交，即使內層捕捉錯誤也不能繼續寫。每次自動重試重新建立預算及暫存區，不沿用前一輪結果。
- 超量回傳既有 Callable 可傳遞的 `failed-precondition` 與「本次尚未寫入、請管理員檢查來源」說明。

## 預算選擇與界線

目前入口仍限定 1–5 品項、兩個候選倉、最多 40 份歷史出貨憑證及既有有界退貨查詢。400 份文件容納現有查核的單份最多 201 筆退貨查詢、40 份出貨憑證及來源／商品／預留／需求／庫存查核；100 次請求與寫入保留餘裕，同時阻擋異常擴張。

這不是 15 品項讀寫預算已驗收：後續須用實際 6–15 品項、多倉、同商品多列、直送及服務混合案例測量讀寫與負載，再決定是否調整。文件位元組大小、索引更新量及 Firestore 平台限制仍由 SDK／後端交易檢查，不能單憑操作計數宣稱全部符合。

正式頁面與角色操作不變；未改數量公式、庫存定義、Rules、Index、Collection、Listener 或 PDF。未部署 Firebase、未啟用正式旗標、未修改正式資料。舊前端收貨仍須依 #308 完成後端切換及正式驗收後另批移除。
