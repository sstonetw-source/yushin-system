# 直送確認共用原採購單來源查核（2026-10-27）

延續 #308 的收貨統一。倉庫入庫已驗證供應 ID 對應的採購單列，直送後端原先只驗證負責人、供應與訂單量，沒有使用同一段 PO 憑證查核；本批抽出共用驗證，補上差異。

## 實際變更

`validateReceiptPurchaseDocument` 由同一份 src 產生到 Receiving runtime，倉庫入庫與直送後端共用。依採購單保存的唯一 supply ID 找到原列，不信任輸入或供應記錄中的列索引；檢查來源訂單、品項、產品、採購數量、倉庫與供貨方式。草稿／documentOnly、取消／結案或連結重複均拒絕。

直送僅在新的 PO 收貨事件前檢查；已存在的 receipt 仍先依原憑證恢復，不因採購單在交易成功後才取消而錯誤重做或阻擋原 ID 恢復。手動採購原本已有自己的權威操作憑證，不改成 PO 契約。

來源不一致的拒絕由 Callable 傳遞為 failed-precondition，提示尚未入帳、請採購確認原單後用原資料重試。驗證在原 Firestore transaction 內，所有寫入仍最後才提交，不新增 writer 或數量公式。

## 角色與資料

正式環境尚未部署本批，操作方式不變。候選後端中：原負責業務／工程師可確認直送，管理員可處理例外；採購與倉管不得代替業務完成直送確認。

成功仍只更新來源品項的實收到貨／送達、供應及需求的實收與 receipt；不增加公司實貨、分倉實貨、在途、批號、成本、庫存異動或預留。來源有誤或越權整筆不寫；兩個同 ID 請求不重複收貨。

直送的 1–5 品項 gate 與其他交易限制不變，本批沒有宣稱 15 品項直送混合已完成。

## 驗證

- 共用 PO witness 測試：唯一連結而非任意列索引，草稿、結案、取消、重複／缺失連結、來源／產品／數量／供貨方式錯配均拒絕。
- 真 Auth → 實際匯出 Callable → Emulator，原採購後端建立 PO；業務與工程師各一來源，管理員完成尾量，非負責人／採購／倉管拒絕。損壞 11 種 PO 狀態或來源後快照不變，首次同 ID 競爭只收一次，PO 後來取消仍可用舊 ID 回讀，新的收貨被拒絕。
- 原 Chrome 1280／390px：沿原 PO 與負責業務確認直送，成功回覆中斷、重新整理同 ID 重試；物理庫存與預留保持不變。
- 倉庫 6／15 品項及商品／服務混合回歸，不因共用抽取破壞既有收貨。
