# PR #503：Excel 可重複分批匯入驗收

## 行為與操作

- 管理員／採購沿用既有入口。價格每批最多 1,000 筆，可立即按「繼續上次價格更新」。
- 主檔每批最多 500 筆，立即重選同一檔案接續；依 SHA-256 指紋辨識工作。
- 移除本機每日累計額度，保留 IndexedDB、Web Locks、完整檔案驗證及差異比對。
- 新檔取代未完成工作仍須確認；已成功的雲端寫入不會回復。
- 主檔在寫入前保存初始工作進度，第一批中斷也能重選原檔接續。
- 價格、主檔及成本共用原 `commitMigrationBatch` writer。匯入操作附上比對基準，每 100 筆異動一個交易；主檔一筆最多包含產品與成本兩份文件。
- 主檔沿用確認預覽時的欄位基準；交易只核對要寫入的業務欄位，衝突即停止該交易。不覆蓋其他未匯入欄位。
- 同一交易內先讀完再寫，產品與成本一起提交。前面已提交的交易不回滾；失敗時不推進本機批次游標。重試先重新讀取伺服器，只補差異。
- 原本其他非匯入呼叫繼續使用原批次寫入路徑。訂單、採購、庫存與角色定義未改。

## 驗證

- `node tools/build-app.cjs`、`node tools/build-app.cjs --check`、`node tools/build-functions-core.cjs --check`。
- `tests/product-price-resume.test.js`：本機解析／資料錯誤、價格 1,000 + 1、主檔 500 + 1、同日接續、同檔重傳、取消／角色切換、IndexedDB 工作隔離、新檔取代、部分完成及回覆遺失後重試、價格衝突與權限失敗。這些是隔離執行真實函式的自動化測試，Excel／網路由測試替身提供。
- 產品識別、前導零、選填價格、成本管理、差異寫入、讀取預算及主檔回歸測試。
- `tests/emulator-product-import.cjs`：真實 Firestore Emulator + 現行 Rules；原子寫入與冪等、預覽衝突、並行交易重試、一般角色偽裝前端管理員仍遭後端拒絕、部分提交後接續。僅允許本機 Emulator，使用 `demo-` 專案。
- CI 的規則檢查工作加入上述 Emulator 驗證；最終必須檢查最新 commit 的 `regression`，不能以舊 commit 的綠燈替代。

## Firebase 讀寫評估

- 價格測試 1,001 筆全部異動：第一批 100 個貨號查詢、1,000 次文件交易讀取、1,000 次文件寫入，交易往返最多 10 批；下一批只處理剩餘 1 筆。重傳同樣資料只查詢，交易讀取及寫入都是 0。
- 既有產品皆唯一匹配的價格批次，N 筆查詢約讀 N 份商品文件，另為 M 筆異動增加 M 次交易文件讀取與最多 M 次寫入。衝突重試會增加讀取；不同廠牌相同貨號可能讓查詢多回傳文件；空查詢仍可能有最低讀取費用。
- 主檔僅依本批貨號／文件 ID 查詢，成本只查 Excel 有填成本的產品。預覽後提交仍重新核對產品身分；提交沿用預覽欄位基準，省去再次整批讀取產品／成本比對。交易額外只讀需修改的產品／成本文件；最多每 100 筆產品讀取 200 份文件。
- Emulator 實測一筆產品與一筆成本：2 次交易文件讀取、2 次寫入、1 個交易；再次提交相同內容增加 2 次核對讀取、0 次寫入。正常重新匯入會先做差異比對，不會為未變資料建立交易。
- 以上是 SDK 實際呼叫／Emulator 驗證的文件操作數，不是正式帳單金額。Rules 的使用者文件相依讀取、空查詢最低費用、網路重試及價目表完成紀錄另計。主檔完成時既有廠牌／歷史紀錄仍可能寫入，即使產品未變；不宣稱整個重傳流程零寫入。
- 沒有新增 Collection、Listener、Functions、排程、跨管理員鎖或 Index。

## 發布界線與限制

- 僅更新 PR；未合併 main、未發布 GitHub Pages、未部署 Firebase 後端、未修改正式資料。
- 不使用 Firebase Hosting，未增加 Hosting 設定或部署流程。
- Rules／Index／Firebase 設定均無需更新。
- 尚未執行正式環境 Excel 寫入驗收；Emulator／測試替身通過不代表正式實測。
- 瀏覽器本機進度不跨裝置；清除網站儲存空間會清除進度，但重新匯入仍先比對雲端。
- Firebase 資源限制與網路失敗仍可能中止本批，應依錯誤訊息重試；沒有人工每日筆數封鎖。
