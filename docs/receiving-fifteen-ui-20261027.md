# 15 品項收貨原畫面驗收（2026-10-27）

沿用 #313 的同一 Receiving Service、後端入口與 receipt 操作識別；本批只新增測試及共用測試來源，不修改產品程式、頁面、角色、數量公式或部署設定。

## 已完成的本機瀏覽器驗收

真實 Chrome 1280px／390px，原 index.html、app.js 與模組，登入實際 Emulator 倉管帳號，透過原「倉庫 → 採購收貨 → 確認收貨」操作。

來源為 14 個商品品項＋1 個服務，同商品分多列、兩個實際倉，單列應收 3 件。原頁面先收第一列 1 件，再收最後商品列 3 件，最後收第一列餘下 2 件。

首次及最後一次：讓 Callable 確認交易成功後，刻意中斷 HTTP 回覆；確認原頁面保留失敗待確認工作。重新整理、登入身份恢復後，按「用原資料重試」，必須送出完全相同的 supplyId／operationId／qty／lotNo／expiryDate，不能由重新整理自動產生新交易。

固定斷言：
- 兩倉合計只入庫／占用 6 件，三份 receipt／lot／受保護成本，五個 HTTP 收貨請求（含兩次重送）。
- 各商品公司／分倉實貨、預留、在途正確；兩個已收完品項移出待收清單，未收品項仍可操作。
- 其餘 12 個商品列及服務列與初始來源完全相同；服務案件、送達及退貨不變。
- 重送前後完整來源、採購需求、供應、庫存、批號與成本快照相同，不重複入庫。
- 倉管畫面顯示「依權限不顯示成本」；Auth 憑證由 SDK 傳送，payload 不帶自訂角色或身份。
- 沒有瀏覽器 pageerror、沒有外部網路請求；原始 SDK／廠商程式由本機測試伺服器提供。

定向瀏覽器 2/2 通過，一般 Node 1,894/1,894 通過，產生檔一致性與 diff 檢查通過。此結果是本機 Emulator 的原畫面驗收，不是正式環境實測；完整 GitHub CI 另列於 PR。

## 共用測試來源與驗收邊界

從 #313 抽出 `tests/fixtures/fifteen-receiving-source.cjs`，供原後端測試與新原站瀏覽器測試共用。來源初始化、PO、在途與需求由 Admin fixture 準備；倉管讀取的是去成本 receivingSupplyOrders 投影，實際收貨一定走原 UI／Auth／Callable／唯一後端 writer。

不能以這批宣稱 15 品項建單 → 初始化 → 正式 PO → 完整履約已全部完成。直送混合、其他交易入口、Preview 實際站與正式切換仍須依 #308 獨立驗收。確認正式後端成為唯一 writer 前，舊 client 收貨不在本批刪除。

測試 runner 新增可選 `--test-name-pattern=regex` 作本機定向執行；預設無篩選，CI 原本的完整集合加上兩個新瀏覽器案例，沒有縮減既有 CI。
